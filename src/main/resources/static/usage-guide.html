The repository includes eight selectable Playwright stories. They open Chromium, enter synthetic data, click through the actual application, check the outcome, and keep the last screen visible briefly so you can explain it. No manual customer-data preparation or provider API key is needed.

First follow Browser automation and automatic test data in the repository README to install the Python browser dependencies. JDK 25 and Maven must be available. Run commands from the repository folder; do not type these commands into the browser address bar.

.venv-browser/bin/python src/test/ui/browser/demo.py --list
.venv-browser/bin/python src/test/ui/browser/demo.py existing-loan
.venv-browser/bin/python src/test/ui/browser/demo.py incident-approve --hold-seconds 30

Choose existing-loan, new-applicant, incident-approve, incident-reject, grievance, document, loan-validation, or applicant-not-found. Choose all for the sequence. Use --slow-ms 800 to slow down actions and --hold-seconds 60 to leave the final screen open longer. The application and browser close automatically afterward.

What to tell your audience: this uses a separate, fresh test application and a deterministic test AI model. The UI, APIs, workers, and review logic are real; customer/tool data and model answers are simulated. Your normal demo's records are not modified. These scripts still need a successful browser execution in a permitted environment; collection alone does not prove the complete journey passes.

1. Before you start

This application demonstrates how several AI-assisted workflows share case tracking, evidence, deterministic rules, and human review. It is a portfolio application, not a connection to your bank. Do not enter your own financial details or anyone else's real information.

  1. In IntelliJ, run the existing AgenticBankingApplication configuration. After Java changes, stop the old run and start it again so the new code is compiled. Wait for “Started AgenticBankingApplication” and port 8080 in the console.
  2. Open the workbench at http://localhost:8080/. If you opened this guide from a file instead of the running server, type that address in your browser.
  3. Look for API connected in the left sidebar. On a phone, the navigation is at the bottom. An empty case list is normal before your first submission.
  4. The full AI journey uses the application's configured model provider. A missing/invalid provider key, quota problem, or unavailable model can produce failure or manual review. That is not an approval or decline based on a customer's creditworthiness. Configure provider credentials outside source control.
What is simulated? Customer records, bureau responses, income checks, and incident actions are demo data/adapters. Agent analysis uses the configured model, unless a separately configured test model is running. The interface does not invent successful results.
Current restart behavior: newly onboarded applicants are stored in application memory and disappear when the app restarts. The three built-in customers return on startup. Cases and approvals also reset in the default memory mode; their optional database mode is configured separately. Refreshing your browser does not restart the app.

3. Your first loan demo — start here

Story: an existing customer wants a loan for home repairs. You are the staff member preparing the request. The system already knows the customer's demo profile.

  1. On Overview, click the Loan review tile. Alternatively choose Start a new case and leave the workflow set to Loan review.
  2. At Find applicant, search for Jane or A001 and click Search. Click Jane Cooper's record.
  3. At Review profile, read the stored income, employer, monthly debt, document references, and source/status. You do not retype these details. Document references such as id.pdf are illustrative names, not uploaded verified files.
  4. Click Continue to loan details. Enter 25000 for amount, home renovation for purpose, and 60 months for term.
  5. Click Review application. Check the summary. Use Edit loan details if you need to change something. Tick the confirmation checkbox only after reviewing.
  6. Click Confirm and submit once. The system creates a case and opens its workspace. Open means queued; Running means processing. Stay on this page; it checks for progress automatically while the tab is visible.
  7. Read What happens next? and the business outcome. Read each agent finding to understand the evidence shown. The optional technical panel contains the raw result for a developer.
  8. If the case is Pending approval, click Go to review queue and follow section 6. Otherwise read the final outcome; do not assume Completed means Approved.
Why these steps? The customer profile describes the person. The loan details describe this particular request. Separating them avoids re-entering the same customer information for every application. The server combines them into a case snapshot.

4. Try a new applicant

  1. Start a Loan review case. Click New applicant? Create a demo customer.
  2. Enter an invented name such as Taylor Example, synthetic SSN suffix 1234, employer Demo Works, annual income 85000, years employed 4, and monthly debt 400.
  3. Click Create applicant. This creates the customer record, not the loan application. The returned profile is marked Declared not verified.
  4. Review it and continue through loan details and confirmation as in section 3.
  5. Before restarting the app, start another loan and search for Taylor. The stored record is reusable.

A duplicate name plus identifier suffix produces an explicit conflict; search for the existing record instead of creating the same person again. New applicants use the existing generic synthetic credit-bureau scenario. This is not a connection to a real bureau or an identity-verification service.

5. Try the other three workflows

Each has a form suited to its domain. Click Use a demo example inside the form to load a synthetic example from the backend. It fills the form only; it does not submit. Review the information and click Submit case yourself. Each example receives a new reference.

Incident response — “A service is having problems”

An incident is an operational issue, such as a loan-service database connection pool becoming full. Choose Incident response → Use a demo example. Inspect the title, description, affected service, and environment. Submit it, then read the diagnosis/remediation information and execution log. An action may be simulated automatically or sent for human review. No real service is repaired.

Grievance redress — “Someone raised a concern”

A grievance is a reported concern. Choose Grievance redress → Use a demo example. Read the invented worker welfare report, project reference, and received-through field. Submit it. Look for the responsible team, illustrative response deadline, and whether human review is needed. A routed/drafted response does not mean an email or message was actually sent.

Do not use real sensitive reports. Restricted handling may intentionally show only generic information.

Document intelligence — “Turn document text into useful facts”

Choose Document intelligence → Use a demo example. This loads synthetic invoice text. Read it and submit. The outcome shows document type, extracted fields, flags, suggested actions, and next queue when available. Confidence is model-reported, not proof of correctness. This screen accepts text; it is not a file-upload or scanned-image OCR screen.

6. Complete human review when the system asks

Not every case creates a review. If the queue is empty, that is normal. A higher-risk application or incident may create one, but policy and model results determine this.

  1. Click Review queue. Refresh if the pending case just finished processing.
  2. Open Review packet for the relevant title/reference. Check the facts, findings, uncertainty, policy checks, and “What your decision does.”
  3. If it says Independent assessment first, record your view before the AI recommendation is shown. This first step does not execute an action. Then inspect the revealed evidence and make a separate final decision.
  4. Click Record a decision. For the demo, a reason code can be DEMO_REVIEWED. Add a note explaining why. Choose Approve or Reject.
  5. After the server confirms, the item leaves the pending queue. Return to Cases, open the associated case, and refresh. The case state reflects the human outcome.
If the packet changed: the app refreshes it instead of silently using your old decision. Read it again. If the backend refuses a decision, its configured reviewer role, expiry, or requester/reviewer separation rule may apply. The UI does not bypass those rules.

An approval is not proof that an external action succeeded. Execution failed is a separate state. Also, the original AI analysis is retained after review rather than rewritten as if the model made a new decision.

8. If something goes wrong

What you seeWhat it usually meansWhat to do
Localhost refused to connectNo server is listening.Run AgenticBankingApplication in IntelliJ and wait for startup on port 8080.
Applicant lookup returns 404 after a code updateThe running app may still use the old classes.Rebuild/restart AgenticBankingApplication; refresh the browser.
401 / 403Backend caller configuration requires authentication or a role.Use the intended local demo run configuration. Do not paste secrets into the form or try to bypass role checks.
Running for a long time / model unavailableModel calls may be timing out, rate-limited, or misconfigured.Check the IDE console and provider configuration. You can leave and return using the case URL.

9. Your try-it checklist

  • Open the workbench and see API connected.
  • Select Jane without typing her income or identity details again.
  • Submit a loan through the review/confirmation step.
  • Refresh the browser on the case page and return to the same case.
  • Read the outcome without needing the technical JSON panel.
  • Create a new synthetic applicant, then find the record again.
  • Try the invoice, incident, and grievance demo examples.
  • If a review is generated, complete it and reopen the case.
  • Explain the distinction between case completion, business outcome, and human approval.

What you can say while showcasing the application

“This demo starts with a customer record rather than re-entering data. Each submission becomes a trackable case. Specialized AI checks return findings, deterministic policy constrains decisions, and important actions can require a human review. The UI makes the next step explicit and preserves the original analysis. External banking adapters are simulated for the portfolio.”

Implementation checks cover UI behavior and contracts where the environment permits. They are not evidence of live-model accuracy or real financial-system integration. If a developer reports a build/runtime restriction, resolve that before expecting new backend features to appear in the running application.
